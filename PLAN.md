# Voice Modem — план разработки

Статус: **черновик на согласование**. Код не пишется, пока план не утверждён.
Открытые вопросы собраны в [разделе 12](#12-вопросы-на-согласование) — у каждого
есть решение по умолчанию, которое будет принято, если возражений нет.

## 1. Что делаем

Веб-приложение — акустический модем. Два человека открывают приложение, соединяются
любым голосовым каналом (телефонный звонок, рация, мессенджер, просто динамик и
микрофон в одной комнате) и обмениваются текстом и небольшими файлами. Данные
кодируются звуком в голосовом диапазоне; скорость и модуляция подстраиваются под
качество канала.

Сервера нет: приложение статическое, работает офлайн после первой загрузки (PWA).
Всё ядро обработки сигнала — на Rust, в браузере исполняется как WebAssembly, в
дальнейшем то же ядро подключается к Android-приложению.

### Не цели (для первой версии)

- Совместимость с существующими протоколами (V.xx-модемы, FreeDV, fldigi, ggwave).
  Протокол свой.
- Передача голоса, видео, потоковых данных.
- Большие файлы. Ориентир — до ~100 КБ (см. таблицу скоростей ниже).
- Автоматический дозвон/управление звонком или рацией (CAT, PTT по кабелю).

## 2. Как это выглядит физически

Браузер не может подмешать звук в сотовый звонок, поэтому сценарии такие:

| Сценарий | Как соединяется | Особенности |
|---|---|---|
| По воздуху | динамик одного устройства → микрофон другого | эхо помещения, шум, слабые динамики |
| Телефон | телефон на громкой связи рядом с устройством с приложением, либо гарнитурный кабель | вокодер (AMR/EVS), шумоподавление, VAD режет «неречевой» сигнал |
| Радио | рация рядом с устройством либо аудиокабель; PTT нажимает человек (или VOX) | полудуплекс, хвост шумоподавителя, предыскажения FM, уход частоты на SSB |
| Интернет | звонок в мессенджере на том же или соседнем устройстве | кодек Opus, потери пакетов, растяжение времени джиттер-буфером, шумодав |

Следствие: самый тяжёлый случай — сотовый телефон через акустическую связку
(вокодер + воздух). Под него нужен очень устойчивый медленный режим.

### Ожидаемые скорости (ориентиры, не обещания)

| Канал | Полезная скорость | 10 КБ файл |
|---|---|---|
| По воздуху, ~1 м, тихо | 0.5–2 кбит/с | 1–3 мин |
| Проводной телефон / G.711 | 1–3 кбит/с | 0.5–1.5 мин |
| Сотовый (AMR/EVS) | 50–300 бит/с | 5–30 мин |
| FM-рация | 0.3–1.5 кбит/с | 1–5 мин |
| SSB (КВ) | 0.1–1 кбит/с | 1.5–15 мин |
| VoIP (Opus) | 0.3–2 кбит/с | 1–5 мин |

Цифры уточняются на этапах 1 и 4 по результатам симуляции и замеров на реальных
каналах.

## 3. Архитектура

```
┌────────────────────────── браузер ──────────────────────────┐
│  UI (TypeScript)                                            │
│   чат · файлы · пресеты · индикаторы канала                 │
│        │ события/команды (postMessage)                      │
│  Web Worker ── WASM: modem-core                             │
│        │ блоки сэмплов (Float32Array, transferable)         │
│  AudioWorklet (тонкий JS: захват с микрофона, очередь       │
│                воспроизведения)                             │
└──────────────────────────────────────────────────────────────┘
```

- **AudioWorklet** только перекладывает сэмплы — никакой логики. Микрофон
  открывается с `echoCancellation / noiseSuppression / autoGainControl = false`.
- **Worker + WASM**: ядро не блокирует ни UI, ни аудиопоток. Обмен через
  `postMessage` с transferable-буферами (SharedArrayBuffer не используем — он
  требует COOP/COEP-заголовков, которых нет на GitHub Pages).
- **Ядро** не знает про браузер: на вход поток сэмплов и команды, на выход поток
  сэмплов и события. Никаких потоков, таймеров и системного времени внутри —
  время измеряется числом обработанных сэмплов. Это делает ядро
  детерминированным, тестируемым и переносимым.

### Структура репозитория

```
crates/
  modem-core/   # DSP, модуляции, FEC, кадры, канальный и транспортный уровни
  modem-sim/    # модели каналов для тестов (шум, полоса, уход частоты, эхо, кодеки)
  modem-cli/    # нативная утилита: текст/файл ⇄ WAV, прогон через симулятор
  modem-wasm/   # wasm-bindgen обёртка над modem-core
web/            # Vite + TypeScript, UI, AudioWorklet, Worker
docs/           # спецификация протокола, заметки по измерениям
```

Зависимости ядра — только чистый Rust (`rustfft` и т.п.), без C-библиотек: это
условие простой сборки под wasm32 и Android.

### API ядра (набросок)

```rust
let mut modem = Modem::new(Config { sample_rate, preset });
modem.push_rx(&samples);              // сэмплы с микрофона
modem.pull_tx(&mut out);              // сэмплы на динамик (тишина, если нечего)
modem.command(Command::SendText(..)); // SendFile, Connect, SetPreset, Abort…
while let Some(ev) = modem.poll_event() { .. }
// события: MessageReceived, FileProgress, LinkState, ChannelStats, TxRequest (для PTT)…
```

## 4. Физический уровень

- Внутренняя частота дискретизации 16 кГц; ресемплер в ядре от/к частоте
  устройства (44.1/48 кГц).
- Рабочая полоса по умолчанию 300–3400 Гц, пресет может сузить её (например,
  500–2700 Гц для рации) или расширить (воздух/интернет — следующая версия).

### Лестница режимов

Один протокол, несколько режимов от «пробьёт что угодно» до «быстро по чистому
каналу». Параметры ориентировочные, фиксируются по результатам симуляции.

| Группа | Модуляция | Скорость (нетто) | Для чего |
|---|---|---|---|
| R (robust) | некогерентная MFSK, длинные символы | ~30–150 бит/с | вокодеры, сильный шум, растяжение времени |
| M (medium) | OFDM, дифференциальная QPSK | ~300–900 бит/с | рация, VoIP, воздух с эхом |
| F (fast) | OFDM когерентная с пилотами, QPSK → 16QAM → 64QAM | ~1–5 кбит/с | чистый воздух, проводная линия |

Опорные параметры OFDM: БПФ 512 на 16 кГц (шаг 31.25 Гц, символ 32 мс) +
циклический префикс 8 мс, ~99 несущих в полосе 300–3400 Гц. Пресеты меняют длину
префикса и набор несущих.

### Кадр

```
[вступительный тон*] [преамбула-чирп] [заголовок] [данные ...]
```

- **Вступительный тон** (опционально, задаётся пресетом) — открыть VOX /
  шумоподавитель рации, «разбудить» VAD вокодера.
- **Преамбула** — ЛЧМ-сигнал (чирп): обнаружение кадра, тактовая синхронизация,
  оценка ухода частоты и частотной характеристики канала.
- **Заголовок** — всегда в самом устойчивом режиме: номер режима данных, длина,
  номер кадра, CRC. Приёмнику не нужно заранее знать режим.
- **Данные** — в режиме из заголовка, с CRC-32.

### Помехоустойчивое кодирование

- LDPC с мягкими решениями (квазициклические матрицы из IEEE 802.11n,
  скорости 1/2, 2/3, 3/4, 5/6) + перемежение + скремблер.
- Для режимов R дополнительно повторение/разнесение по времени и частоте.
- Запасной вариант, если LDPC не уложится по срокам: свёрточный код K=7 с
  декодером Витерби.

### Синхронизация и компенсации

Уход тактовой частоты звуковых карт (до сотен ppm), уход несущей (SSB — до
±200 Гц), АРУ и изменение уровня, оценка и выравнивание канала по пилотам.

## 5. Канальный уровень

- **Полудуплекс** по умолчанию: станции передают по очереди. Причины: рации с PTT;
  собственное эхо (динамик слышен в свой микрофон); вокодеры плохо переносят
  двойной разговор.
- **ARQ**: селективное подтверждение пачки кадров, повтор только потерянных;
  таймауты рассчитаны на задержки каналов (VoIP, сотовый — сотни мс).
- **Доступ к среде**: слушаем перед передачей (детектор занятости), случайная
  задержка при коллизии.
- **Режим PTT**: ядро выдаёт событие «нужна передача», UI показывает крупную
  подсказку «Нажмите PTT», передача начинается по кнопке/пробелу; для VOX —
  автоматически с вступительным тоном.
- **Вещательный режим** (без обратного канала): передача без подтверждений с
  избыточностью — для односторонних каналов и записи/воспроизведения.
  В первой версии — простое повторение; фонтанные коды — позже.

## 6. Адаптация к каналу

1. **Зондирование при установлении связи.** Обмен зондирующими кадрами в режиме R:
   чирп + многотональный сигнал. Каждая сторона измеряет ОСШ по частотам, АЧХ,
   разброс задержек, уход частоты, искажения и сообщает результат партнёру.
   По результатам выбираются стартовый режим, полоса и маска несущих.
2. **Непрерывная подстройка.** В каждом подтверждении приёмник сообщает свежие
   измерения (ОСШ, запас декодера, долю потерянных кадров) и рекомендуемый
   режим. Передатчик понижает режим быстро (после 1–2 неудач), повышает
   осторожно (после серии успехов и при наличии запаса по ОСШ).
3. **Независимо по направлениям**: каналы часто несимметричны.
4. **Аварийный откат**: при потере связи обе стороны возвращаются к режиму R.
5. Позже: побитовая загрузка несущих (разная модуляция на разных частотах).

Адаптацию можно отключить и зафиксировать режим вручную (нужно для вещательного
режима и отладки).

## 7. Транспортный и прикладной уровень

- **Сессия**: приветствие (версия протокола, позывной/имя, возможности),
  зондирование, обмен, завершение. Возможна работа без сессии — одиночное
  сообщение в устойчивом режиме.
- **Текст**: UTF-8, сжатие коротких сообщений, статусы «отправляется → доставлено
  / не доставлено».
- **Файлы**: предложение (имя, размер, хеш) → согласие получателя → блоки →
  проверка хеша. Прогресс, оценка оставшегося времени, отмена, докачка после
  обрыва. Сжатие (deflate), если даёт выигрыш.
- Текстовые сообщения имеют приоритет и вклиниваются в передачу файла.

## 8. Пресеты

Пресет — набор стартовых параметров и ограничений; адаптация работает внутри него.

| Пресет | Полоса | Стартовый режим | Разрешённые режимы | Особенности |
|---|---|---|---|---|
| По воздуху | 300–3400 Гц | M | R, M, F | длинный циклический префикс (эхо) |
| Телефон | 300–3400 Гц | R | R, M (F — только если зондирование покажет чистую линию) | вступительный тон, непрерывный «речеподобный» спектр против VAD |
| Радио FM | 500–2700 Гц | R | R, M, F | PTT/VOX, вступительный тон 300–500 мс, учёт предыскажений |
| Радио SSB | 500–2500 Гц | R | R, M | поиск ухода частоты ±200 Гц, устойчивость к замираниям |
| Интернет | 300–3400 Гц | M | R, M, F | устойчивость к потерям пакетов и растяжению времени, увеличенные таймауты |
| Свой | — | — | — | все параметры вручную |

## 9. Веб-приложение

- Vite + TypeScript + React. PWA (офлайн, установка на домашний экран).
  Публикация на GitHub Pages.
- **Экран чата**: лента сообщений и файлов со статусами, поле ввода, прикрепление
  файла, прогресс передачи.
- **Панель связи**: пресет, состояние (ожидание / зондирование / приём /
  передача), текущий режим и скорость, ОСШ, индикаторы уровня входа/выхода с
  предупреждением о перегрузке.
- **Диагностика** (сворачиваемая): спектр/водопад, созвездие, АЧХ канала,
  журнал кадров.
- **Настройки**: устройства ввода/вывода, громкость, имя/позывной, ручной выбор
  режима, PTT/VOX.
- **Мастер настройки уровня**: тестовый сигнал → подсказка «тише/громче».
- Языки интерфейса: русский и английский.
- Браузеры: актуальные Chrome/Edge/Firefox на десктопе, Chrome на Android,
  Safari на iOS (с оговоркой: iOS не везде позволяет отключить обработку
  микрофона — проверяется на этапе 2).

## 10. Тестирование

- **Юнит-тесты** DSP-блоков, FEC, кадров.
- **Симулятор канала** (`modem-sim`): белый шум, полосовой фильтр, уход частоты
  и такта, многолучёвость, замирания, клиппирование, потери/растяжение блоков.
  Кривые «доля ошибок от ОСШ» для каждого режима — как регрессионные тесты в CI.
- **Реальные кодеки**: прогон WAV через Opus / AMR / G.711 (ffmpeg) — отдельный
  необязательный набор тестов.
- **Сквозные тесты**: два экземпляра ядра через симулятор — чат, файл, обрыв,
  адаптация вверх и вниз.
- **Натурные замеры**: по воздуху, через реальный звонок, мессенджер, рации.
  Результаты — в `docs/`.
- CI (GitHub Actions): `cargo fmt/clippy/test`, сборка wasm, линт и сборка веба.

## 11. Этапы

Каждый этап заканчивается работающим проверяемым результатом.

| № | Этап | Результат |
|---|---|---|
| 0 | Каркас | workspace, CI, сборка wasm, пустое веб-приложение на GitHub Pages |
| 1 | PHY-минимум | один режим R (MFSK) + преамбула + кадр + FEC; `modem-cli` кодирует текст в WAV и декодирует обратно; тесты через симулятор |
| 2 | Веб-минимум | звук в браузере; односторонняя передача текста по воздуху между двумя устройствами; индикаторы уровня и спектр |
| 3 | Канальный уровень | полудуплекс, ARQ, сессии; двусторонний чат со статусами доставки; режим PTT |
| 4 | Быстрые режимы и адаптация | OFDM (M, F), LDPC, зондирование, автовыбор и смена режима на лету |
| 5 | Файлы | передача файлов, прогресс, отмена, докачка, сжатие; вещательный режим |
| 6 | Пресеты | настройка под каждый канал по симуляции кодеков и натурным замерам |
| 7 | Доводка | PWA, мастер уровня, локализация, документация протокола |
| — | Позже | Android (ядро через UniFFI/JNI + Oboe), шифрование, полный дуплекс с частотным разделением, фонтанные коды, побитовая загрузка несущих, широкополосные режимы |

Главные риски: (1) сотовые вокодеры и шумоподавление в мессенджерах могут
оставить только десятки бит/с — проверяется рано, на этапе 1, прогоном через
кодеки; (2) обработка звука в браузерах/ОС, которую нельзя отключить (особенно
iOS) — проверяется на этапе 2; (3) объём работы этапа 4 — он самый большой и при
необходимости делится на «M-режимы» и «F-режимы».
